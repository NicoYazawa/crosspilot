# 可观测持久化接线与成本归因

## 概述

**现象**：可观测三件套（回放 / 对比 / 成本）的后端接口、表结构、读取侧聚合逻辑都已完备，
但跑完真实查询后 `observability` 四张表**全为 0 行**——接口返回的是空集而不是报错，
所以从接口层面看不出任何异常。这是典型的「装好了但没通电」。

**根因**：写入链路上有**六个**互相独立的断点，任何一个不通，全程都是静默的：

| # | 断点 | 表现 |
|---|---|---|
| 1 | `Emitter.Run(ctx)` 全仓无调用点 | `Emit` 只把记录推进 1024 缓冲 channel，无人消费 |
| 2 | token 用量在四个环节被丢光 | 事件落库了，但成本恒为「无用量」 |
| 3 | `observability.cost` 无 INSERT 路径，`internal/pricing` 零 import | 即使有 usage 也无处定价、无处落库 |
| 4 | `CreatedAt` 单位写成纳秒，契约是秒 | 整批写入必然失败，而失败被计入 dropped 静默吞掉 |
| 5 | `Emitter.Close()` 的 `select` 可能丢队列 | 退出时最后一批已收下的记录不落库 |
| 6 | 装配根丢失 provider 名 | 成本行缺 provider，无法查价格表 |

**范围**：`internal/agent/{llm,protocol,orchestrator,observability}`、
`internal/application/orderflow`、`internal/infra/persistence/pg`、
`internal/container`、`internal/pricing`（新增）、`internal/config`、
`frontend/{nginx.conf,features/shop,features/observability}`。不改任何对外 JSON 契约的字段名。

## 一、诊断过程

### 1.1 缺陷 1：`Emitter.Run` 从未被调用

```
$ grep -rn '\.Run(' --include=*.go | grep -i emitter
（仅有 emitter.go 自身注释与 emitter_test.go）
```

[container.go](../../../internal/container/container.go) 构造了
`agentobs.NewEmitter(pg.NewObsSink(pool, logger), …)`，
[ports.go](../../../internal/application/orderflow/ports.go) 每条事件都调 `Emitter.Emit`——
**但 `Run` 没有任何生产调用方**。

`Emit` 本身不写库，它只 `select` 进 `e.queue`（容量 1024）。没有 `Run` 消费，
记录就在 channel 里堆到满，然后被计入 `dropped` 计数器。**跑完一轮真实查询，四张表 0 行。**

这个缺陷之所以难发现，是因为 `Emitter` 自己的日志说「丢弃了 N 条」——而没人去看那条日志；
从 HTTP 接口看，`/observability/runs/{id}/replay` 只是返回空数组，与「这轮确实没事件」不可区分。

### 1.2 缺陷 2：token 用量在四层被逐层丢弃

用量没有「丢在一处」，它在每一层的结构体里都不存在，于是被自然过滤掉：

| 环节 | 现状 |
|---|---|
| `internal/agent/llm/wire.go` | `wireResponse` 无 `usage` 字段，`parseWireResponse` 只取 Content/ToolCalls |
| `internal/agent/protocol/protocol.go` | `Step` / `Response` 无 usage 字段 |
| `internal/agent/orchestrator/orchestrator.go` | `model_turn` 事件只带 `resp.Content` |
| `internal/application/orderflow/ports.go` | payload 是手拼白名单 map，上游没加就不会透传 |

四层各自都「看起来正常」，只有把它们连起来看才发现：上游响应里的 `usage` 对象
一路到不了数据库。修复必须**四层同时打通**，只改一层仍然全零。

### 1.3 缺陷 3：成本表没有写入方

```
$ grep -rn 'INSERT INTO observability.cost' --include=*.go
（仅出现在 *_test.go 中）
```

`pg.CostStore` 只有读方法；`internal/pricing`（`LoadFromFile` / `PriceBook.Lookup` /
四维 `TokenKind`）**零 import**——没有价格表 YAML，没有配置项，是一份完整的死代码。

读取侧却是完备的：`application/observability/cost.go` 的 `CostOfRun` 会正常聚合 CostEvent，
只是永远聚合到空集 → `/observability/runs/{id}/cost` 恒返回 `total_calls: 0`。
**读侧完备 + 写侧全无**，是这次最容易被误判成「功能已实现」的形态。

### 1.4 缺陷 4：`CreatedAt` 单位错（修 1、2、3 之后才暴露）

打通前三个断点后，事件仍然不落库。查 `pg` 侧：

```go
// SinkRecord.CreatedAt 的契约是 Unix 秒
func unixSecToUTC(sec int64) time.Time { return time.Unix(sec, 0) }
```

而 emitter 写的是：

```go
CreatedAt: ev.CreatedAt.UnixNano(),   // ← 纳秒
```

纳秒值经 `time.Unix(sec, 0)` 还原后年份溢出到 int64 微秒表达不了的范围，
pgx 序列化直接失败，**整批写入全丢**。而 `Emitter` 把这个失败计入 `dropped` 后继续跑，
日志里只有一行计数器——不查库就永远发现不了。

### 1.5 缺陷 5：`Close()` 可能丢弃队列中已收下的记录

`run()` 的 `select` 在 `e.closed` 与 `e.queue` 同时就绪时**随机**选一个分支。
关闭时若选中 `closed`，队列里已 `Emit` 成功、调用方认为「已记录」的记录会被整体丢弃。

这条是被 `TestForward_用量与身份透传到观测副本` 逼出来的：该用例的失败信息是
「观测副本缺少事件」——**一开始误判为测试问题，实际是它照出了真实缺陷**。

### 1.6 缺陷 6：装配根丢失 provider

`buildDecisionProvider` 里局部变量 `pc.Name`（qwen/deepseek/…）只在该函数内可见；
`llm.Config` 与 `llm.Client` 都没有 provider 字段。成本行需要 `provider + model`
才能查价格表——**没有 provider 就没有成本归因**。

## 二、修复

### 2.1 用量贯穿四层

新增 `protocol.Usage`，挂在 `Step` 上（`fakemodel.Step = protocol.Step` 别名自动获得该字段，
测试可直接脚本化用量）：

```go
// JSON 标签刻意与 observability.cost 的列名逐一对应——payload 里的用量字段名
// 与成本表列名同形，读事件与读成本行时不必做心智映射。
type Usage struct {
    TokensIn        int64 `json:"tokens_in"`
    TokensOut       int64 `json:"tokens_out"`
    TokensCached    int64 `json:"tokens_cached"`
    TokensReasoning int64 `json:"tokens_reasoning"`
}
```

`llm/wire.go` 按 OpenAI 兼容协议解析（`prompt_tokens` / `completion_tokens` /
`prompt_tokens_details.cached_tokens` / `completion_tokens_details.reasoning_tokens`），
**缺失即零值、不报错**：上游不返回用量是常见情况而非失败，由下游按「未定价」显式记录。

用量放在事件 payload 而非 `runevent.Event` 的独立字段——payload 已是事件数据的既有位置，
这样 **SSE 线上、journal 回放、观测副本三处拿到的是同一份字节**，回放与成本天然对得上。

### 2.2 成本定价：装配根的装饰器

新增 `internal/container/cost_sink.go`，一个 `agentobs.Sink` 装饰器包住 `pg.NewObsSink`。

选它的理由：
- `internal/pricing` **只能被装配根引用**（`tools/arch/arch_test.go` 规定 agent / infra /
  application 都不得依赖它），装饰器必须住在 `container`
- Emitter 完全不动，保持「对价格一无所知」的纯粹职责，agent 层零改动
- 估算发生在后台 flush 批处理里，不在 `Emit` 同步路径上，不触碰 F6「埋点不阻塞」闸门

**F4「unpriced 显式」判定规则**（写进代码注释与测试）：

- 某维 token 数为 0 → 不需要该维价格，缺条目**不算 unpriced**
- 某维 token 数 > 0 但价格表无该条目 → `unpriced = true`、`cost_minor = 0`、`priced_at = NULL`
- 上游没返回 usage（全零）→ 同样 `unpriced = true`（「我们不知道花了多少」≠「不花钱」）
- 已定价：`cost_minor = Σ(tokens_k × unit_k)`，在 **decimal 域内求和后一次性取整**

provider/model **随每次响应传递**而非装配时固定（`payload.Provider` 优先于配置值），
这样故障转移到另一家 provider 时成本仍归到正确的价目行。

### 2.3 落库：同事务、先事件后成本

`pg.ObsSink.Append` 在 `insertEvents` 之后、`Commit` 之前插入成本行：

```go
// 必须在 insertEvents **之后**：cost.event_id 有外键指向 event.event_id，
// 反过来写会撞「事件行还不存在」。同一个事务里，顺序就是全部约束。
```

`ON CONFLICT (event_id) DO NOTHING` 保幂等，按 64 条一批走 `pgx.Batch`。

### 2.4 Emitter 生命周期

```go
emitterCtx, cancelEmitter := context.WithCancel(context.Background())
emitter.Start(emitterCtx)
```

**必须用独立 ctx，不能用 Build 收到的信号 ctx**：`Run` 的退出路径用「Run 收到的那个 ctx」
去 flush，信号 ctx 在退出时已被取消，最后一批会以 `context.Canceled` 全部丢掉——
而这正是「关了但没落库」的隐蔽形态，且因为错误被 `errors.Is(err, context.Canceled)`
静默跳过，日志里什么都看不到。

`Close` 的顺序：先 `emitter.Close()`（关 `closed` → Run 走 flush 分支 → 此时 emitterCtx
仍存活 → 落库成功），**再** `cancelEmitter()`，最后才是 Redis / Pool。

`run()` 的 `closed` 分支补 `drainQueued`，把队列里已收下的记录全部收进本批再写（缺陷 5）。

### 2.5 价格表：内嵌 + 可覆盖

新增 `internal/pricing/default_pricing.yaml`，用 `go:embed` 作为默认表，
`PRICING_PRICEBOOK_PATH` 可覆盖。

选内嵌而非外挂文件：容器镜像里不需要额外 COPY/mount，避免「文件没进镜像 → 全表 unpriced」
这种静默降级。

**⚠️ 表内价格待人工核对。** 文件头已写明来源 URL、生效日期与三条取价规则。

### 2.6 成本精度：最小货币单位由「分」改为 1e-6 元

`cost_minor` 的**字段名与列名一律不改**，改的只是「最小单位」的定义。

理由：按真实价目，一次下单查询总成本约 **0.48 分**，按分取整后**每一行都是 0**——
成本看板长期低报，正是 F4 要防的那类静默失败，也让 F3「与账单偏差 < 1%」不可能成立。

这个改动有个很实用的副作用：**厂商价目表按「元 / 百万 tokens」报价，而在
「最小单位 = 1e-6 元」下，该数字与「每 token 多少最小单位」逐个相等**
（1 元/百万 tokens = 1e6 最小单位 / 1e6 tokens = 1）。于是价格表可以原样抄厂商价目，
人工复核时不需要做任何心算换算。

新增迁移 `0005_cost_unit_micro`（仅 `COMMENT ON COLUMN`，无结构变更）。

### 2.7 前端两处

**订单 / 历史页恒为空**：`recordRun` 有实现、有导出、有单测，但**没有任何调用方**。
它坏在「没人调用」而不是「调用出错」，所以页面不报错、控制台不报错——只是永远显示
「暂无订单」，看起来像新账号还没下过单。修法是 `useChat` 增加 `onRunSubmitted` 回调，
在 POST 成功、run_id 确定之后触发；写失败只 `console.error`，不影响主链路
（IndexedDB 是本地缓存，不是事实源）。

**`/observability/*` 经 nginx 返回 `200 + index.html`**：`location /` 的 `try_files`
把接口路径兜成了前端页面。不代理 `/observability/` 本身是**刻意的安全决策**
（见 nginx.conf 末尾长注释：返回 journal 原始事件，含 buyer_id / session_id / query，
且 run_id 是 `run_<unixNanos>` 可按时间戳穷举），但返回 200 的 HTML 会让调用方
以为接口存在、只是解析失败，把「刻意不暴露」伪装成「前端路由」。改为显式 404。

## 四、遗留与诚实边界

**本轮能证明的**：真实调用的事件与成本确实写进了 Postgres，读接口确实读得出来，
换算与公开价目一致。

**本轮不能证明的**：

1. **F3「与真实账单偏差 < 1%」未验收。** 该门禁要求与厂商实际出账对账，
   需要外部账单数据，本轮不具条件。目前验到的是「用量被正确采集、按表换算无误」，
   **这不等于与账单对账通过**。「测试绿灯」与「效果达标」是两件事。
2. **价格表未经人工核对**（`default_pricing.yaml` 头部已标 ⚠️）。表内数字按公开价目
   填写并注明来源与生效日期，**需人工复核后**方可作为成本依据。
3. **F6 埋点不阻塞**：本轮只在真实链路观察到主流程无可见延迟，
   未做注入式压力验证（如 sink 持续变慢时 `Emit` 的降级行为）。

**顺带发现的既有缺陷（本次未改）**：`Taskfile.yml` 中 `check` 目标定义了两次
（第 111 行的含 `frontend:check`，第 296 行的不含并覆盖前者），
即 `task check` 实际**不跑前端校验**。属既有问题，不在本次范围。

**部署形态的代价**：三件套接口不在容器部署中经 nginx 暴露，
因此交付界面里的 Replay / Cost / Diff 面板在容器部署下拿不到数据。
要让它们可用，得先给这组接口真正的鉴权（或让前端携带令牌），
而不是靠「不代理」兜底——这仍是 P7 的待办。
