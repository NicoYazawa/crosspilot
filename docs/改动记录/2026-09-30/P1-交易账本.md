# P1：交易账本

日期：2026-09-30
范围：交易账本（正确性核心）。Postgres 事务模型重设计、四张聚合表、两阶段提交、条件更新扣减、SessionClaim CAS、租约与心跳、哈希与快照摘要。

原始证据在 `eval/verification/2026-09-30-P1-验收记录.md`，本文件说明为什么这么写、修掉了哪些上一阶段绿着但没用的东西。

## 计划

P1 的核心命题：**没有 SQLite 的 BEGIN IMMEDIATE 单写锁，Postgres MVCC 怎么保证「同一时刻只有一个写者在改一笔交易」**。

写锁换成三件套：

1. **唯一约束**：`trade_confirmations.operation_id` 唯一。同一操作编号只可能有一行确认单，因此「两个写者各自为同一 operation_id 准备确认单」在数据库层就只剩一个能落地。
2. **条件更新扣减**：`UPDATE trade_sku_inventory SET stock = stock - $qty WHERE sku_id = $1 AND stock >= $qty AND unit_price_minor = $3 AND currency = $4`，`rowcount != 1` 即失败。报价与库存是同一行的两个字段，确认单看到的就是扣减时校验的。
3. **咨询锁**：确认单路径走 `pg_advisory_xact_lock(operation_id)`，把「检查后写入」的窗口在数据库层关闭，而不是靠应用层假设。

金额一律最小货币单位（分）的整数；浮点不进数据库，也不进账本——与 P0 的 `Money` 域保持一致。

## 实现

### 领域层 `internal/domain/{trade,canonical,session}`

- **`trade.Pure` 域**：确认单的两阶段提交纯逻辑放在 `domain/trade`，不碰数据库——并发与事务的失败模式在数据库层验证，而校验、规范化与摘要这些最容易写错的地方可以在毫秒级单测里穷举。
- `Prepare`：`规范化 → 算摘要 → 幂等重放判定 → 过期判定 → 报价与库存核对`。**幂等重排必须先于报价核对**：重试一笔刚扣过库存的请求时，价格已变/库存已因该交易下降，于是「同一次重试」被判成 PRICE_CHANGED / INSUFFICIENT_STOCK——幂等语义就被打穿了。
- `Resolve`：`SnapshotHash` 校验 → 状态判定（**先于过期检查**）→ 过期 → 投票 → 执行。「幂等读取先于过期检查」这条语义是源项目逐字保留的。
- **`canonical`**：值对象哈希用的规范编码。键升序、无空白、非 ASCII 不转义、拒绝浮点、时间截到微秒。摘要覆盖的时间与币种都按 UTC 归一，否则数据库读回的 `timestamptz` 携带会话时区会让同一时刻算出两个不同摘要。
- `SnapshotMatches` / `SnapshotEqual`：`hmac.Equal` 恒时比较。摘要虽然是 SHA-256，但输入是有限的字段集，比较必须与输入长度无关。

### 持久层 `internal/infra/persistence/pg`

- **四张聚合表**（`migrations/0002_trade_ledger.up.sql`）：`trade_sku_inventory` / `trade_confirmations` / `orders`+`order_lines` / `trade_operations`。`ck_trade_stock_nonnegative` 与 `ck_orders_cancelled_has_reason` 等 CHECK 约束是最后一道防线——它们保证「即使有人绕过应用层直连数据库」也写不出负库存或没原因却已取消的订单。
- **`trade_store.go`**：`Prepare` / `Resolve` / `Confirmation` / `Order` / `InitializeInventory` / `Claim` / `Save` / `AssertOwner` / `Load`。`operationID` 用 SHA-256 摘要作为咨询锁的 key。
- **`session_store.go`**：`(session_id, owner_id, revision, fence)` CAS。`Claim` 让 `fence` 前进；`Save` 用 `(revision, fence)` 条件更新；迟到的旧票据写入必然 `RowsAffected() != 1`，被映射成 `session.ErrStaleWrite`。
- **`trade_snapshot.go`**：把订单快照转成对外形态（`OrderSnapshot`），包含 `AmountScope=merchandise_only` 与 `OrderKind=purchase_intent` 两个常量字段，前端与契约不应当被自由文本污染。
- **`migrate.go`**：迁移执行器沿用 P0 的实现。

### 租约 `internal/infra/lease`

P1 实现了租约本体与「丢失 → 作废本地执行权 → 取消生产者」这条语义。**`SERVER_RESTART` 的落库留给 P4**（理由见下）。

租约不是权威判据。Redis 可能因为网络分区或主从切换认为租约已易主，持有者并不知情。真正的最终防线是 `session_write_claims` 的条件更新；租约的作用是把「这种情况」变成「尽早发现」而不是「唯一保证」。

设计参数：`TTL` 默认 30s、`Heartbeat` 必须严格小于 TTL（默认 5s）、`WaitTimeout` 默认 30s。`Watch` 每两个心跳+1 次后还没成功续约就主动作废——对应「本进程长时间暂停」这一情形，暂停期间续约没有发生，恢复后与其继续写不如先把自己作废。

### 应用层 `internal/application/trade`

编排层把领域纯逻辑与持久层组合起来；这一层只为 P3 的 Agent 路径存在（P1 阶段是空架子，仅为占位与防止领域逻辑被人直接绑到持久层）。

## 回归：本轮修掉的真缺陷

### 1. 容器泄漏——次跑测试新建一个 Postgres 容器，进程退出不关

P0 验收时只跑过一次性集成测试，本轮大规模测试暴露：每个 `go test` 进程创建一个 `postgres:18-alpine` 容器，但 `Admin(t)` 拿到的 `adminContainer` 变量全程没人调过 `Terminate`，挂在工区里就成了 30+ 个 `happy_pascal` / `jolly_spence` 之类的随机命名容器。

**根因**：`testcontainers` 的回收器（ryuk）默认开启，但 `harness.go` 把 `TESTCONTAINERS_RYUK_DISABLED` 设成 `"true"`——语义反了，"true" 在该环境变量名里代表"禁用 ryuk"。于是兜底也没了。

**修复**：直接挂进程退出钩子。具体做法：

- 写一个 `Ensure(*testing.M)` 给 `TestMain` 调，`m.Run()` 返回后 `Terminate`；
- 在 `internal/infra/persistence/pg/main_test.go` 加 `TestMain`，复用 `pgtest.Ensure`；
- 把 `harness.go` 的注释与实现重新对齐——`TESTCONTAINERS_RYUK_DISABLED` 现在**默认开启** ryuk，留作进程崩溃的兜底，正常退出由 `Ensure` 兜底。

中途走过的弯路：曾试过把 `Terminate` 挂在 `t.Cleanup` 上——子用例结束就触发，结果**第一个子用例的退出把后续子用例依赖的容器关掉了**。refcount 方案尝试过，但因为「同一个测试进程里父测试与子测试 Cleanup 链的触发顺序」与「Admin 调用次数」并不严格一一对应，会出现 refcount 已归零但仍有用例没跑。**只有「整个测试进程退出」这一个时点是对的**，Go 测试里它对应 `TestMain` 的 `m.Run()` 返回。

验证：跑完整套件后 `docker ps -q | wc -l` 从 0→0；中途不再有「happy_pascal / jolly_spence」积压。

### 2. 幂等重放排在报价校验之后

`Prepare` 的旧顺序是「报价核对 → 库存核对 → 写确认单 → 返回权限」。重试一笔刚扣过库存的请求时，价格已变/库存已因该交易下降，于是「同一次重试」被判成 PRICE_CHANGED / INSUFFICIENT_STOCK——幂等语义被打穿。

**修复**：顺序改为「规范化 → 算摘要 → 重放判定 → 过期判定 → 报价与库存核对」。`TestPrepareReplayPrecedesExpiryAndQuotes` 验证空库存/报价已变/有效期已过/三者同时四种情况下都 `Replayed=true`。

### 3. 摘要覆盖的时间未归一到 UTC

内存里算出 `+00:00`，从数据库读回算出 `+08:00`（数据库会话时区），同一时刻两个摘要。决议永远过不了快照校验。

**修复**：`Prepare` 与存储层读写都按 UTC 归一。`TestDigestSurvivesDatabaseRoundTrip` 由红转绿。

### 4. 金额换算的小数位符号写反

`canonical` 的 `decDigitsFor` 对除零位币种外的多数币种返回 `-1`，让 `decimal` 抛错。改为返回每币种的小数位整数。`TestMoneyRoundingHalfEvenAcrossCurrencies` 现在覆盖 USD/EUR/JPY/CNY 四种。

### 5. 会话租约 `Logf` 为 nil 时 panic

`New` 里把 nil Logf 默认成空闭包，避免第一次 Acquire 成功时崩在 `m.logf(...)`。

### 6. `Release` 后仍可续约

`Release` 旧实现只置 `released=true`，没置 `valid`，导致 `Renew` 还能打到后端并成功——一次正常结束的执行被算成「还持有执行权」，真正抢到键的人反被延长了别人的租约。修复：归还即失效，置 `valid=false` 并关闭 `stopWatch`。

## 真实外部链路

- testcontainers 起 `postgres:18-alpine`，每个测试建独立库并执行迁移；
- B1–B7 全部走真实数据库，**非 mock**——结果断言只对「`count(*) = 1`」「库存 = 0」这种数据库读回的状态做判定，并发正确性的唯一来源是数据库约束而不是应用层某把恰好生效的进程内锁；
- 容器由 `pgtest.Ensure` 在进程退出时回收，ryuk 兜底 panic 路径。

### B8 的临界状态

同一台机器上的实测：

```
跑完整套件 + 全部 pg 包 → P50=12.97ms P95=18.38ms（不达预算）
单跑 B8 用例 → 第 1 次 P95=12.08ms；第 2 次 P95=9.58ms
```

全量套件并行跑时机器负载高、容器端口映射抖动大（`[::1]:32772` 这类用户态转发是主要成本）。**B8 在单跑时稳定达标，但与其他并发用例同时跑会落在预算边界**。

按项目约定「测试通过 ≠ 外部服务可用 ≠ 生产效果达标」——这里**如实标注**：

- **生产端口映射成本**：本机 Docker Desktop 走用户态转发，跨主机直接 socket 通信则没有这部分开销。**生产环境的具体数字需要 P8 的 docker compose I1 验收时重测**。
- **未优化的可能方向**：减少每笔事务的 SQL 数、复用会话级 prepared statement、把 `BenchmarkLedgerWrite` 与 P95 测试分开跑等。本轮没动——理由是 B8 是「性能验收」而非「性能优化」，P1 的核心是「不出错」。

## 已知缺口（不得以「测试通过」掩盖）

1. **`SERVER_RESTART` 事件的落库不在 P1**。计划 P1 第 7 条写「租约丢失 → 取消生产者并写 SERVER_RESTART」。逐字核对源实现后确认：30s/5s 这对常量与 `SERVER_RESTART` 属于 **AG-UI 运行日志租约**（`ag_ui_runtime.py`，P4 范围）；而 Redis 会话租约的实际参数是 **30s 租期 + 10s 心跳**（`lease_ms=30000`、`max(10, lease_ms//3)`），丢失时 `invalidate()` + `cancel()` 并**不写任何事件**。P1 因此只实现了租约本体与「丢失 → 作废本地执行权 → 取消生产者」语义；事件落库留给 P4。租期与心跳做成了构造参数（默认 30s / 5s），改默认值不需要动代码。
2. **`isUniqueViolation` / `retryableUniqueError`**：只在 `insertConfirmation` 真的撞唯一约束时才被调用，而咨询锁把同一 `operation_id` 的并发插入串行化了，黑盒集成测试无法构造这个冲突。这条路径的「退化成重放」语义目前只有代码可读，没有测试背书——要测它需要一个测试专用的注入点。
3. **租约的丢失路径只在假后端上验证**。`internal/infra/lease` 的测试用的是内存后端；真实 Redis 上的 Lua 原子性、网络分区、主从切换下的语义没有实测。Redis 侧只有一个「连接不上时返回包装错误、不 panic」的用例。
4. **`initialize_inventory` 的历史订单占用迁移路径没有真实历史数据可验**。测试里用直接写 SQL 的方式造出「订单存在但库存行不存在」的状态；真实迁移（从旧库导入）没有演练过。
5. **`-race` 未在宿主上执行**。本机无 C 编译器且 `CGO_ENABLED=0`，`go test -race` 直接报错。CI 的 Linux job 有 gcc，会跑完整竞态检测；纯逻辑包的竞态检测是通过容器离线跑过的（`canonical`、`lease` 等包已确认全绿），但这不是宿主 toolchain 的结果。
6. **`-race` 未覆盖集成测试的并发**。32/100 并发的验收用例本身在无竞态检测下运行。并发正确性目前的背书来自数据库约束与「恰好 1 笔 / 恰好 10 单」这类**结果断言**，而不是竞态检测器。
7. **并发争抢下的延迟未纳入验收**（P95 76.5–80.7 ms）。原因是口径问题：这条实测里包含 TCP 端口映射、连接排队与行锁等待，其中只有行锁等待属于账本本身。把它混进同一条门槛，只得到一个与账本实现无关的数字。
