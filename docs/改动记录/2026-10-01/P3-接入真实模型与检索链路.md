# P3 阶段一：接入真实模型，打通「搜索 → 商品卡片」

## 概述

**触发问题**：前端输入「登山包」，`POST /commerce/ag-ui/run` 返回 500 `submit_failed`。

**排查结论**：这不是一个断点，是四个叠在一起。任何一个单独修好，页面上仍然看不到商品：

| # | 断点 | 证据 |
|---|---|---|
| 1 | 模型网关从未实现 | 仓库内无任何 LLM HTTP 客户端；`cfg.LLM`（四家 provider、超时、重试、校验）完整却**零消费者** |
| 2 | 14 个工具零 handler | `internal/agent/tools/*.go` 只有 `*ToolDef()` schema；全仓库 `.Register(` 只出现在 `_test.go` |
| 3 | 接口无法承载真实模型 | `DecisionProvider.Next(prompt string)` 只收裸字符串——无工具 schema、无对话历史、无 `ctx` |
| 4 | A2UI 卡片到不了前端 | `runevent.Kind` 里没有 `a2ui`，而前端 `useChat.ts` 正等着 `ev.kind === 'a2ui'` |

**本阶段范围**：输入「登山包」→ 模型自主调用 `product_search_tool` → 检索已导入的 3,700 件商品 →
前端渲染出真实商品卡片。**下单链路留待阶段二。**

**不含**：D5–D10（HITL 审批、四级 token 预算、流中段限流恢复、Skill 注册表、偏好版本冲突、
dislike 全量注入）、anthropic 的 Messages API 适配器、`task_dispatch_tool` 三代理架构、
Qdrant 向量检索、middleware 链装配。

## 一、实现

### 1.1 新增 `internal/agent/protocol`（叶子包）

模型交互的类型从 `fakemodel` 里搬出来。`fakemodel` 的包注释自称「**测试用**的确定性 fake LLM」，
生产接口却返回它的类型，是把测试夹具当协议用。

`fakemodel` 改用类型别名，其 50 处既有引用零改动编译通过。`protocol` 只依赖标准库，
自己定义最小 `ToolDef`，不 import `tools`。

`protocol.ErrModelUnavailable` 是 sentinel：「没配模型」与「这次调用失败了」必须能分开——
混成一个会让运维去排一个不存在的故障。

### 1.2 改造 `DecisionProvider` 与 orchestrator 历史

```go
type DecisionProvider interface {
    Next(ctx context.Context, req protocol.Request) (protocol.Response, error)
}
```

`Orchestrator` 新增 `SystemPrompt` / `Tools` 字段。`Run` 维护 `[]protocol.Message`：用户输入打头，
每轮追加一条 assistant 消息（含它发起的调用）与若干条 `role:"tool"` 消息。
原先的 `buildNextPrompt`（把 Turn 序列化成 JSON 拼在 prompt 后面）删除。

### 1.3 新增 `internal/agent/llm`（OpenAI 兼容适配器）

`Chat Completions`，只用标准库（`agent` 层的 vendorDeps 只有 uuid，引第三方要改架构规则）。
覆盖 qwen / deepseek / minimax 三家（协议同族）。

- `arguments` 是 JSON **字符串**，需二次解析；空串 / `null` 归一成 `{}`。
- `content` 可能是 `null`（纯工具调用回合）→ 用 `*string` 接。
- 只对瞬时错误重试（网络、429、5xx）；4xx 直接返回。
- 重试耗尽**不**包装成 `ErrModelUnavailable`——上游抖动不能伪装成「你没配密钥」。
- 错误信息不含密钥；超长错误体截断到 512 字节。

### 1.4 新增 `internal/agent/prompts`

主 agent 系统提示词，用 Go 常量而非 embed+YAML（`agent` 层无 yaml.v3 依赖）。
从源项目 `globex-agent/app/application/prompts/globex.yml` 的 `main_agent` 段移植，
**只描述本阶段真正具备的能力**（`product_search_tool`），不写一堆不存在的工具。

### 1.5 `product_search_tool` handler

**落点：`internal/container/toolhandlers.go`**（偏离计划，见第三节）。

两个必须绕开的陷阱：

1. **`TopK` 缺省值要在 handler 里补**：schema 写的 `default` 只是给模型的建议，模型省略时 JSON 里
   根本没有该字段，反序列化得 0，而 `ProductSearchSpec.Validate` 要求 `TopK ∈ [1,100]`。
2. **`SearchResult` 没有 json tag**：直接 marshal 得到 `Hits` / `RecallStrategy` 这样的大写键名，
   过不了 `ToolRequiredFields` 的小写校验。handler 按 snake_case 自行组 map。

`toolFailure` 一律返回 **nil 的 Go error**：orchestrator 在 `execErr != nil` 时会中止整个 run，
而「参数不对」「没搜到」是模型能自我纠正的中间状态。

### 1.6 A2UI 卡片打通

- `runevent.KindA2UI Kind = "a2ui"`。
- 新增 `orderflow.SearchEmitter`：复用既有 `Column` 根 + `ProductCard` 结构。
- `Bridge.forwardSearchA2UI` 在 `tool_result` 且 `ToolName == product_search_tool` 时补发 A2UI 事件。
  可行性来自 `orchestrator.summary()` 在成功态返回 handler 的**原始 JSON**，Bridge 直接反序列化
  `event.Content` 取 `hits`。

### 1.7 错误码分类：500 → 503

`handler.go` 按 `errors.Is(err, protocol.ErrModelUnavailable)` 回 **503 `model_unavailable`**，
其余保持 500。原有「submit 失败 = 500」的断言改成断言分类后的行为，而非放宽断言。

### 1.8 环境变量命名修正

`config` 读 `LLM_QWEN_API_KEY`（`provider()` 拼 `"LLM_"+suffix+"_API_KEY"`），而 compose / `.env`
用的是**不带前缀**的名字。改部署文件对齐 config：config 是代码内契约，且已有测试钉住。

compose 的 `environment:` 是内联的、没有 `env_file`，`.env` 只参与 `${...}` 替换、**不会自动进容器**，
所以必须写「宿主短名 → 容器前缀名」的映射。

顺带修两处坏语法：
- `.env:11` 的 `QWEN_API_KEY=${QWEN_API_KEY:-}` 是自引用（永远为空）；
- `docker-compose.yml` 的 `${QWEN_API_KEY:-${LLM_API_KEY}:-必须设置…}` 嵌套默认值不合法。

### 1.9 前端读懂错误码

`useChat.ts` 原先失败只 `setError('submit ' + status)`。改为读响应体的 `{"error": code}`，
`model_unavailable` 给出可操作提示，其余回显状态码与错误码；响应体不是 JSON 时退回裸状态码，
不让「显示提示」本身崩掉。

提示文案**不点名某一家供应商**，而是指向决定用哪家的那个变量：
「请在 .env 里填 `LLM_DEFAULT_PROVIDER` 所选那家的 API key（如 DEEPSEEK_API_KEY / QWEN_API_KEY）」。
初版写死了 `QWEN_API_KEY`——改用 DeepSeek 的人会照着提示去配一个没人读的变量。

## 二、过程中查出的缺陷

以下都不是「顺手清理」，每一个都会让阶段目标失败或让失败被掩盖。

### 2.1 `assistantMessage` 回放空的 `tool_call_id`（会让上游 400）

补 orchestration 的 history 累加用例时立刻红了：

```
合成的调用 ID = [ ]，期望 [call_1_0 call_1_1]
第 0 个 tool 消息的 tool_call_id = "call_1_0"，与 assistant 里的 "" 不匹配
```

工具结果消息用的是**合成 ID**（模型没给 ID 时补 `call_<iter>_<idx>`），而 assistant 消息回放的
是模型的原始 ID（空）。两个 ID 对不上，OpenAI 兼容端点会以 400 拒掉整个请求，且报错只说
「tool_call_id 不存在」，很难联想到是这里发散的。

**修法**：`assistantMessage` 改收 `iteration`，走同一个 `toolCallID`。

### 2.2 前端 `ProductCard` 读 `price_minor`（卡片没有价格）

后端两份 emitter（`a2ui.go` 与 `a2ui_search.go`）都发 `price_major`，来源是
`catalogsearch.ProductCard.PriceMajor`；`price_minor` 是**交易账本**侧的词
（`unit_price_minor`，分），A2UI 这一层没有生产者。

两侧各自的测试都用自己的键名，边界上错了谁都不会红。`grep` 全仓确认无任何
`price_minor` 生产者后，改前端读 `price_major`，并顺带渲染 `brand` / `category`、
把 `product_id` / `sku_id` 挂到 data 属性上。

### 2.3 A2UI 根 Column 缺 `children`（卡片一张都不显示）

前端的 `Renderer` 只对 `type=Column` 的节点解析子组件，且子节点来自 **`props.children` 里的
组件 id 数组**；`List` 组件只渲染 `props.items` / `props.data`（纯数据条目），不解析子组件。

而两份 emitter 的根 Column 都没有 `children`，也都用一个 `List`（`items-list` / `results-list`）
来「装」卡片。结果：卡片组件全都在 `components` 里、四条校验全过，页面上只有一个「(空 Column)」。

**修法**：新增共用构造 `a2uiRoot(title, children, extra)`，根 Column 显式列出全部卡片 id；
删掉容纳不了卡片的 `List`。**确认单那一路（`a2ui.go`）是同一处缺陷**，一并修。

### 2.4 A2UI 事件载荷多包了一层

原先发 `{"messages":[三条报文]}`。前端的 `A2UIMessageSchema` 是
`z.discriminatedUnion('action', ...)`——载荷必须**就是**一条报文。包一层会被判成
「A2UI 报文不合规」整块渲染失败，而失败原因指向前端 schema。
改为**一条报文一个事件**（三条报文三条事件）。

### 2.5 `catalogsearch` 旧用例 panic 吞掉整个包

```go
assert.Len(t, result.Hits, 1)                        // 断言失败但继续
assert.Equal(t, "P1001", result.Hits[0].ProductID)   // panic: index out of range
```

一次召回失败会让整个包的后续用例一条都不跑——**失败会伪装成「全部通过」**。
改成 `require.Len`。

这个缺陷是在变异测试里暴露的：变异 C1（`tokenize` 不切二元组）的输出只有一条 FAIL、
后面两个用例连 `=== RUN` 都没出现。

### 2.6 handler 放行只有空白的检索词

`normalized_query: "   "` 会通过「三个字段至少有一个」的检查，然后 tokenize 出一批空白 token
去全表扫一遍。补 `strings.TrimSpace`。

**这一条是写测试时发现的**——用例先红，才回头改实现。

### 2.7 `catalogsearch` 缺「二元组重叠」这条召回用例

既有用例查的是「登山」（**子串**，最宽松的匹配），而买家实际输入「登山包」、库里叫「登山背包」：
两者谁都不是谁的子串，唯一重叠是二元组切出来的「登山」。

补两条：`..._CJK二元组重叠`（必须召回）与 `..._无重叠则不召回`（必须搜不到）。
后者是前者的反面：若 `keywordScore` 变成「有词就中」，只有后者能挡住。

### 2.8 一次操作事故：`git checkout --` 误回退 `ports.go`

变异测试后我用 `git checkout -- internal/application/orderflow/ports.go` 还原，把该文件退回了
**HEAD 版本**——本会话的改动还没提交，因此丢掉了 `Cancel` / `running`（P5 的取消能力）、
观测通道接线与 `forwardSearchA2UI`。测试立刻以 `b.Cancel undefined` 报出来，已逐段重新应用
并对齐内容（该文件 176 行 → 258 行）。

**教训**：还原变异要用备份副本（`cp file file.bak`），不要用 `git checkout`——工作区里
未提交的改动会被一起冲掉。

## 三、与计划的偏差

**必须报告**：以下三处与已批准的计划不一致。

### 3.1 handler 落在 `internal/container`，不在 `internal/application/agenttools`

计划第 5 步写「新包落在 `internal/application` 前缀下，无需改 `arch_test.go`」。**这条是错的。**

`tools/arch/arch_test.go` 里 `application` 组件的 `projectDeps` 是
`["internal/domain", "internal/agent"]`——**不含 `internal/application` 自身**，
所以 application 层的包不能 import 同一层的 `catalogsearch`。已核实：`internal/application/`
内部零跨子包 import。

handler 恰好既要 `catalogsearch.UseCase` 又要产出 `agent` 层的 `tools.ToolResult`。
`container` 是唯一被允许同时看见两者的地方（`projectDeps: ["internal"]`），
它的职责本来就是「把接不上的东西接起来」。文件头注释已写明原因。

### 3.2 未做工具结果的字段裁剪

计划的风险一节写「handler 进模型的那份结果做字段裁剪（保留 product_id/sku_id/title/…，
去掉 description 等长字段）」。**没有做。**

原因：A2UI 报文与模型读的是**同一份** payload（`orchestrator.summary()` 返回 handler 的原始 JSON，
Bridge 反序列化它取 `hits`）。裁剪掉字段会同时让卡片少掉品牌、类目、图片。
本阶段 `top_k` 默认 5，上下文膨胀风险有限。

若将来 `top_k` 上到几十，正确做法是在 Bridge 侧区分「给模型看的」与「给前端画的」两份，
而不是牺牲卡片信息量。

### 3.3 提示词：移植范围比计划更窄

计划写「移植 `main_agent` 段（156 行中的前 100 行）」。实际只移植与检索相关的段落，
并新增一节「本阶段不具备的能力」。理由：提示词里描述不存在的工具会让模型反复调用它们，
每一步都拿到 unknown tool——这比「提示词不够详细」代价更大。

## 六、遗留

- **下单链路**（`create_order_tool` + 确认单 + A2UI 确认卡）——阶段二。
  确认单的 A2UI 渲染链路本阶段已顺带修好（§2.3）。
- **anthropic Messages API 适配器**：配置里保留，选中它时按「未接入」回 503，
  而不是拿一个必然 400 的请求去打它。
- **思考模式的 `reasoning_content` 回传**：DeepSeek 等供应商在思考模式下，要求把助手消息的
  `reasoning_content` 在后续请求里原样带回，否则可能 400。本适配器没有这个字段，因此
  **思考模式的模型暂不可用**。要用的话，需要在 `protocol.Message` / `Response` 加该字段、
  在 `wire.go` 双向透传，并补一条「第二轮请求带回了上一轮的 reasoning_content」的用例。
  本阶段默认的 `deepseek-chat` / `qwen3-max` 都是非思考模式，不受影响。
- **`task_dispatch_tool` 三代理架构**：本阶段让主 agent 直接调 `product_search_tool`。
