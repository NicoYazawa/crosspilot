# 商品目录数据落地（修「商品库是空的」）

## 概述

站点报「商品库是空的」。排查下来不是一个断点，而是**四层叠在一起**的断链，
任何一层单独修好都仍然是空的：

1. **数据文件从未进仓库** —— 计划里点名的种子 `catalog-v3.jsonl` 根本不在 `data/`；
2. **导入器的结构体是照着不存在的模式写的** —— 即使有文件也解不出任何一行；
3. **没有任何代码调用导入器** —— `BootstrapLoader`、`CatalogRepo` 的调用方都是零；
4. **库存从未初始化，且下单读不到第二个规格** —— 目录有 3,700 件商品，
   但只有 3,700/7,105 个规格能真正下单，另一半被判「规格不存在」。

数据来源：源 Python 项目 `D:\1_Projects\Python\globex-agent\data\catalog-v3.jsonl`
（4,785,235 B、3,700 行），gzip -9 压到 `data/catalog-v3.jsonl.gz`（309,851 B，约 15 倍）。

## 一、四层断链的定位与修复

### 1.1 数据文件落地

`data/catalog-v3.jsonl.gz` 入库（3,700 行）。存压缩版而非明文：明文 4.6 MB 进 git，
每次改动都在历史里留一份；压缩后 0.31 MB，且加载器自带 gzip 魔数嗅探，明文同样能直接喂。

**为什么两个格式都要能读**：运维手头往往是解压后的明文，图省事不该被格式卡住。
`openCatalogFile` 读前两字节判断魔数（`0x1f 0x8b`），是 gzip 就套一层解压，否则原样读，
不设任何开关。

### 1.2 导入器的模式对齐

`jsonProduct` 之前是为一个**虚构的扁平模式**写的，源数据是嵌套的：

```jsonc
// 源数据（真实形状）
{
  "product_id": "P1001", "title": "...", "category": "travel",
  "skus": [ {"sku_id":"P1001-S1","spec":"军绿色","currency":"CNY","price_major":189.0,"stock":50},
            {"sku_id":"P1001-S2","spec":"沙漠黄","currency":"CNY","price_major":199.0,"stock":30} ],
  "rating_summary": {"average": 4.7, "review_count": 128},
  "highlights": [...], "dimensions_cm": {...}, ...
}
```

按真实形状重写后，字段落位规则（`toRow()`）：

| 库列 | 取值 |
|---|---|
| `id` | `product_id` |
| `category_id` | `category` |
| `price_amount_major` / `price_currency` | **`skus[0]`** 的价格与币种 |
| `default_sku_id` | `skus[0].sku_id` |
| `in_stock` | 任一 SKU 的 `stock > 0` |
| `rating` / `review_count` | `rating_summary.average` / `.review_count` |
| `attributes` | **完整 `skus` 数组** + `highlights` + `dimensions_cm` + `tax_category` + `external_product_id` + `source_updated_at` |
| `image_url` | 留空（源数据没有图片字段，不编造） |

关键约束：**`price_amount_major` 与 `default_sku_id` 必须取自同一个 SKU**。
一个取 S1 的价、另一个指向 S2，确认单上的报价就与它钉住的规格对不上。

金额用 `json.Number` + `dec.UseNumber()` 读入，保留十进制字面量：`189.0` 不能变成
`189`，更不能沾上浮点噪声（`199.0` → `199.00000000000003`）。

### 1.3 规格落法：单规格表 + 全量存 attributes（有损，已决策）

`catalog.products` 是单规格表（0003 迁移：一个 `price_amount_major` + 一个 `default_sku_id`），
而源数据里 **3,405/3,700 件商品（92%）有两个规格、两个不同价格**。已确认的处置：

- 商品行取 `skus[0]` 作默认规格与报价；
- 完整 `skus` 数组原样写进 `attributes` JSONB。

**不动迁移、不动交易读模型**，代价是表上的主价格只代表首个规格——但完整规格明细
没有丢，读端（见 1.4）从 `attributes` 还原全部规格。这是一次**有损但可逆**的降级：
它没有把「还有第二个规格」这件事从库里抹掉。

### 1.4 下单读不到第二个规格（真实功能缺陷）

`pg.Catalog.Find` 之前只返回硬编码的默认规格（`Spec: "默认规格"`）。账本侧
`trade_sku_inventory` 是按规格建的行，下单要拿 `sku_id` 去核对报价与库存，于是——

> 目录里 7,105 个规格有库存，只有 3,700 个能下单。第二个规格被
> `quoteOf` 判成「商品 P1001 的规格 P1001-S2 不存在」。

修法：`Find` 增读 `attributes`，交给新的 `orderableSKUs` 还原全部规格；
`attributes` 缺失/损坏/为空时**退回单规格**——库里权威的价格与 `default_sku_id` 仍在，
这件商品依然可下单，只是少掉「还有别的规格可选」。属性坏掉不该让整件商品不可下单。

规格解析规则（`internal/domain/catalog/attributes.go`）刻意放在**领域层**：两个读取方
（按 ID 读单件的 `pg.Catalog`、批量列的 `CatalogRepo`）必须对同一列有同一套理解。
各写一份的后果不是重复代码，而是两份逐渐分叉的规则。

parse 的两条边界被刻意分开：

- 没有 `skus` 键 / 数组为空 → `nil, nil`，表示「这件商品没有规格明细」；
- `skus` 存在但形状不对 → **报错**。把它也当「没有规格」，就会把一行损坏的数据
  静默降级成一个看起来正常的单规格商品。

### 1.5 库存从未初始化

`trade.InitializeInventory` 已在端口/服务/存储三层实现并测过，但**生产代码里零调用者**。
后果是下单时 `quoteOf` 报「SKU 不存在或尚未初始化持久库存」。

`cmd/catalog-import` 的 `seedInventory` 补上这一步：**从 DB 读回商品**（`ListAll`）而不是
从文件读——只导商品不导库存时，账本才是事实源；再按文件重算会凭文件覆盖已发生的扣减。
无规格的商品**统计为跳过，而不是补一条主价格**：库存种子里 `stock` 是必填的，
凭空给一个数字就是编造可售数量，会在下单时变成真实的超卖。

`InitializeInventory` 的语义保住了幂等：新 SKU 得到 `stock - occupied(CONFIRMED)`；
已有 SKU 只刷新报价/标题，**从不重置库存**。所以重启容器重跑导入不会把卖出去的库存复活。

### 1.6 接线：compose 启动时自动导入

```dockerfile
ENTRYPOINT ["sh", "-c", "/app/crosspilot-migrate up && /app/crosspilot-catalog-import && exec /app/crosspilot"]
```

启动时若 `catalog.products` 非空则跳过（幂等），另提供 `cmd/catalog-import -force` 强制重导。
`Taskfile.yml` 加 `catalog:import`（`FORCE=1` 触发 `-force`）。

## 二、实测证据（compose 栈，从空库起）

```
$ docker compose up -d --build           # 空库 → 自动播种，约 2 秒
$ docker compose exec -T postgres psql -U crosspilot -d crosspilot -A -F'|' -c "..."
products|3700
in_stock|3330
no_default_sku|0
currencies|5
categories|8

inventory_rows|products_with_inventory|total_stock
7105|3700|263410
```

规格分布：**2 个规格的商品 3,405 件，1 个规格的 295 件**（与源数据一致）。

P1001 抽查：`price_amount_major` 字面量为 `189.0`（未被规范化成 `189`），
`default_sku_id` 为 `P1001-S1`，两个规格都在 `attributes.skus` 里，中文文本逐字节完好。

端到端：下单 → 确认 → 决议，`unit_price_minor` 18900、数量 2、`total_amount_minor` 37800；
决议后订单 `CONFIRMED`、总计 `899.00 CNY`，库存 20 → 19。

**幂等验证**：再次运行导入后 P1002-S1 仍为 19（已售出的库存没有回来）——
这一点重要，因为 ENTRYPOINT 在每次容器启动时都会跑导入。

## 六、已知限制（未做，如实记录）

1. **`catalog.products` 仍是单规格表。** 主价格与 `in_stock` 只代表首个规格，
   按价格排序、按库存过滤这类**表级**查询看到的是首个规格的视角。完整规格
   在 `attributes.skus` 里，读单件商品没问题，做聚合查询会有偏差。正解是建
   `catalog.product_skus` 表，属迁移改动，不在本轮范围。
2. **前端没有商品列表接口。** 界面上的商品只来自 agent 流式推送的 A2UI 卡片，
   没有「浏览商品库」的入口——即使库里已有 3,700 件。要看列表得走
   `GET /commerce/*`，且 agent 链路仍被 P3 模型网关桩（`unavailableModel`）挡着。
   这属新功能，不在本轮范围。
3. **`image_url` 全部为空**，因为源数据没有图片字段。刻意留空而不是塞占位图：
   塞了之后无法分辨「有图」和「占位」。
