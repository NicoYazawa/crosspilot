## A1 冷启动 < 1s

命令：

```bash
./bin/crosspilot-server.exe &          # CROSSPILOT_HTTP_ADDR=:18001
# 轮询直到 /health 返回首个响应，记录耗时
```

输出：

```
首次响应耗时：376 ms
HTTP 503  {"status":"down","checks":{"db":"down","redis":"down"}}
--- 二次探测（依赖仍不可用）---
HTTP 503
耗时 84 ms
```

结论：**通过**。首次响应 376 ms，且这是「依赖全部不可达」时的值——依赖正常时更快。
该数值是「进程启动 + 首个 /health 响应」的端到端耗时，比单纯计时进程启动更严格。

过程发现：首轮实现耗时 2160 ms（不达标）。原因有二：健康探测串行执行；Redis 客户端
在失联时按默认策略重试 5 次拨号（每次都要等一个拨号超时）。修复见「回归」一节。

## A2 依赖断开时 /health 返回 503 且含 db: down

命令：

```bash
task docker:up
task migrate:up
./bin/crosspilot-server.exe &          # CROSSPILOT_HTTP_ADDR=:18002
curl -s http://localhost:18002/health
docker compose stop postgres
curl -s http://localhost:18002/health
docker compose start postgres
curl -s http://localhost:18002/health
task docker:down
curl -s http://localhost:18003/health
```

输出：

```
=== 1. 依赖齐备 ===
{"status":"ok","checks":{"db":"up","redis":"up"}} <- HTTP 200
=== 2. 仅停掉 Postgres ===
{"status":"down","checks":{"db":"down","redis":"up"}} <- HTTP 503
=== 3. 恢复 Postgres（服务未重启）===
{"status":"ok","checks":{"db":"up","redis":"up"}}|200 <- 恢复后
=== 4. 进程始终未退出 ===
服务进程仍在运行（PID 151）
```

依赖全停时：

```
{"status":"down","checks":{"db":"down","redis":"down"}} <- HTTP 503
```

结论：**通过，且强于验收要求**。除「全停返 503」外，额外证实：
- 单项依赖失败时能区分到具体依赖（`db: down` 而 `redis: up`），不是一律报错；
- 依赖恢复后无需重启进程即回到 200；
- 依赖失联期间进程不退出、不进入重启循环。

## 端到端链路（真实外部服务）

```
=== 迁移 ===
迁移方向 up，实际执行 1 步
=== 再执行一次（幂等）===
迁移方向 up，实际执行 0 步
=== 回滚 ===
迁移方向 down，实际执行 1 步
=== 重新升上去 ===
迁移方向 up，实际执行 1 步
```

对真实 Postgres 18 执行迁移：首次应用 1 步、重复执行 0 步（幂等）、回滚 1 步、再升 1 步。
容器版本：postgres:18-alpine、redis:8.8.2-alpine、qdrant/qdrant:v1.19.0。

敏感配置透传：`docker compose ps` 在未设置 `POSTGRES_PASSWORD` 时直接报错
（`required variable POSTGRES_PASSWORD is missing a value: 必须设置 POSTGRES_PASSWORD`），
不会以明文默认值启动。

## 回归：本轮修复的两处性能缺陷

| 缺陷 | 修复 | 证据 |
|---|---|---|
| 首轮 `/health` 耗时 2160 ms | 探测并发执行 + 整轮预算 1s；Redis 关闭内部重试与拨号重试 | 376 ms / 84 ms |
| Redis 客户端日志绕过结构化日志直写 stderr | 客户端日志转接 `log/slog`，按 debug 级别输出 | 日志中不再出现裸 stderr 行 |
