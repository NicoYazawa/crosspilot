## B1 并发幂等：N=32 并发同一 OperationID → 恰好 1 笔交易

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 \
  -run TestConcurrentSameOperationCreatesExactlyOneTrade -v -timeout 10m
```

输出：

```
=== RUN   TestConcurrentSameOperationCreatesExactlyOneTrade
--- PASS: TestConcurrentSameOperationCreatesExactlyOneTrade (2.41s)
ok  github.com/NicoYazawa/crosspilot/internal/infra/persistence/pg  2.599s
```

用例实际断言的内容（任一不成立即失败）：

- 32 个并发请求（每个一个独立的 `*pg.Store` 实例，共享连接池但不共享任何内存状态）
  **全部返回同一张确认单**（逐个比对 `confirmation_id`）；
- 直接查库：`SELECT count(*) FROM trade_confirmations WHERE operation_id = 'operation-shared'`
  **恰好 1 行**；
- 决议该确认单后 `orders` / `order_lines` / `trade_operations` **各恰好 1 行**；
- 库存从 `concurrency*4` 只减少 2（即只扣了一次）。

结论：**通过**。并发路径因此只能依赖数据库（咨询锁 + 唯一约束 + 幂等重放），
而不是依赖应用层某把恰好生效的进程内锁。

## B2 库存不超卖：100 并发抢 10 件 → 恰好 10 单成功，库存 = 0

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 \
  -run TestConcurrentBuyersCannotOversell -v -timeout 10m
```

输出：

```
=== RUN   TestConcurrentBuyersCannotOversell
--- PASS: TestConcurrentBuyersCannotOversell (2.98s)
ok  github.com/NicoYazawa/crosspilot/internal/infra/persistence/pg  3.197s
```

用例实际断言的内容：

- 成功决议**恰好 10 笔**（等于库存件数），其余 **恰好 90 笔**返回 `INSUFFICIENT_STOCK`；

unit_price_minor = ? AND currency = ?`），以 `rowcount != 1` 判定失败，
因此「够不够」由数据库在持锁状态下回答。

## B4 幂等读取顺序：重试已提交的 OperationID → 返回原结果，不新建第二笔

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 \
  -run 'TestPrepareReplayReturnsExistingEvenWithNewExpiry|TestHashAndDecisionReplayAreEnforced|TestPendingExpiresButCommittedReplayRemainsValid' -v
```

输出：

```
--- PASS: TestPrepareReplayReturnsExistingEvenWithNewExpiry (0.14s)
--- PASS: TestHashAndDecisionReplayAreEnforced (0.14s)
--- PASS: TestPendingExpiresButCommittedReplayRemainsValid (0.15s)
```

断言的关键点：

- 用**新的有效期**重放同一 operation id，返回的是原确认单，**新有效期被忽略**
  （`ExpiresAt` 与原值逐字段相等）；
- 已决议的确认单在**时钟推进 24 小时后**仍幂等返回首次结果；
- 同一决议重复提交幂等；相反决议返回 `DECISION_CONFLICT`；
- 未决议的确认单过期后，**同意与拒绝两条路径**都返回 `CONFIRMATION_EXPIRED`
  （过期是「这份价格不再可信」，与用户点的是同意还是拒绝无关）。

结论：**通过**。「幂等读取先于过期检查」这条顺序语义在实现里是显式的：
`trade.Resolve` 在 `Status != pending` 时直接返回，`ExpiresAt` 判定在其之后。

## B5 价格漂移防护：prepare 后改价 → resolve 失败并返回 PRICE_CHANGED

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 \
  -run TestPriceDriftAfterPrepareRejectsResolve -v
```

输出：

```
=== RUN   TestPriceDriftAfterPrepareRejectsResolve
=== RUN   TestPriceDriftAfterPrepareRejectsResolve/价格变化
=== RUN   TestPriceDriftAfterPrepareRejectsResolve/币种变化
--- PASS: TestPriceDriftAfterPrepareRejectsResolve (0.28s)
```

断言：两条路径（改价 12900→9900、改币种 CNY→USD）都返回 **`PRICE_CHANGED`**，
库存未被扣减，三张结果表均为 0 行。

**实现细节**：条件更新只说「条件不成立」，不说「哪一条不成立」。
因此扣减失败后会**在同一个事务里复读一次库存行**，据此区分
`PRICE_CHANGED`（价格/币种不符）与 `INSUFFICIENT_STOCK`（库存不足）。
把「价格变了」报成「库存不足」会让调用方去改数量，而真正该做的是重新生成确认单。

结论：**通过**。

## B6 栅栏拒绝迟到写：租约过期后旧执行者写回 → ErrStaleWrite

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 -run TestSessionClaimRejectsStaleWrites -v
```

输出：

```
=== RUN   TestSessionClaimRejectsStaleWrites
--- PASS: TestSessionClaimRejectsStaleWrites (0.31s)
```

断言：

- 第一次 `Claim` 得到 `fence = 1`，第二次（另一实例）得到 `fence = 2`；
- 用第一次的票据 `Save` → **`ErrStaleWrite`**（迟到的旧执行者被拒）；
- 当前执行者用新票据 `Save` 成功；
- 保存后 `revision` 前进 1，再用同一张旧票据保存被拒，**库里仍是第一次写入的内容**；
- 8 个并发 `Claim` 得到**唯一且恰好 1..8 的 fence**（无重复、无缺号）；
- 其他买家 `Claim`/`AssertOwner` → `ErrOwnerMismatch`；
- 归属校验**不推进 fence**（读取会话不应该把正在执行的写者作废）；
- 快照非 JSON 对象（空串、非 JSON、数组、字符串、数字）→ `ErrCorruptState`。

结论：**通过**。

## B7 冲突重试：≤3 次后放弃并告警

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 -run TestConflictRetryIsBounded -v
```

输出：

```
=== RUN   TestConflictRetryIsBounded
=== RUN   TestConflictRetryIsBounded/冲突次数在上限内时成功
=== RUN   TestConflictRetryIsBounded/冲突超过上限时放弃并给出明确错误
=== RUN   TestConflictRetryIsBounded/业务失败不触发重试
--- PASS: TestConflictRetryIsBounded (0.44s)
```

断言：

- 注入 2 次 `SQLSTATE 40001`（序列化失败）后第 3 次成功；
- 持续注入时**恰好尝试 4 次**（首次 + 3 次重试）后失败，错误信息含「重试」字样，
  且整段耗时 < 5s（证明确实是**有界**退避，不是指数增长或无限重试）；
- 确定性业务失败（库存不足）**只尝试 1 次**——不把必然失败的操作白重放三遍。

**注入的错误是真实的 `*pgconn.PgError{Code: "40001"}`**，不是自定义类型：
重试判据读的是 SQLSTATE，拿别的错误类型测出来的「能重试」在真实冲突下未必成立。

结论：**通过**。

命令：

```bash
go test ./internal/infra/persistence/pg/ -count=1 -run 'TestLedgerWriteP95UnderBudget|TestLedgerIdempotentReplayP95UnderBudget' -v -timeout 30m
```

输出（两次独立运行）：

```

账本写入延迟：P50=9.2301ms  P95=12.0846ms P99=13.1021ms MAX=17.3965ms（样本 200）
幂等重放延迟：P50=2.255ms   P95=2.9629ms  P99=3.2729ms  MAX=3.3395ms （样本 200）

--- 第 2 次 ---
账本写入延迟：P50=8.7802ms  P95=9.577ms   P99=10.0602ms MAX=17.3405ms（样本 200）
幂等重放延迟：P50=1.98ms    P95=2.5024ms  P99=2.5448ms  MAX=2.5751ms （样本 200）
```

结论：**通过**。P95 在 **9.58–12.08 ms** 之间波动，两次都低于 15 ms 的预算。
两次相差 2.5 ms（约 26%），因此这里报的是区间而不是单次数字——
单次采样不足以支撑结论。

采样口径：每次迭代走**完整写入链路**（prepare + resolve），
覆盖咨询锁、比较更新扣减、订单与订单行写入、决议记录。取 200 个样本，
分位点用最近秩法（不用插值：插值会给出一个从未真实发生过的延迟数字）。

### 并发争抢（参考值，不计入验收）

```
并发写入延迟（8 写者 × 40 笔，含连接排队与端口映射开销）：
P50=20.085ms  P95=76.5341ms P99=118.2763ms MAX=145.8435ms
连接池上限 = 8，即并发窗口被限制在 8 条连接上；该数值不代表账本本身的开销
```

**为什么不拿它做判定**：B8 的原文是「账本写入 P95 < 15ms（单实例，本地 Postgres）」，
它给定的是单实例、单请求的写入延迟，没有给并发 SLA。这条实测里包含 TCP 端口映射、
连接排队与行锁等待，其中只有行锁等待属于账本本身。把它混进同一条门槛，
只会得到一个与账本实现无关的数字。该用例仍保留一条兜底断言（MAX < 1s），
用于发现锁泄漏这类数量级异常。

## 回归：本轮修掉的两处真缺陷

| 缺陷 | 后果 | 修复 | 证据 |
|---|---|---|---|
| 幂等重放排在报价校验之后 | 重试一笔刚扣过库存的请求时，价格已变/库存已因该交易下降，于是「同一次重试」被判成 `PRICE_CHANGED` / `INSUFFICIENT_STOCK`——幂等语义被打穿 | 顺序改为「规范化 → 算摘要 → 重放判定 → 过期判定 → 报价与库存核对」 | `internal/domain/trade` 的 `TestPrepareReplayPrecedesExpiryAndQuotes`：空库存/报价已变/有效期已过/三者同时四种情况下都 `Replayed=true` |
| 摘要覆盖的时间未归一到 UTC | 内存里算出 `+00:00`、从数据库读回算出 `+08:00`（数据库会话时区），同一时刻两个摘要 → 决议永远过不了快照校验 | `Prepare` 与存储层读写都按 UTC 归一 | `TestDigestSurvivesDatabaseRoundTrip` 由红转绿 |

另有金额换算的小数位符号写反（除零位币种外全部报错）、
会话租约 `Logf` 为 nil 时 panic、`Release` 后仍可续约三处缺陷，
详见 `docs/改动记录/2026-09-30/P1-交易账本.md` 的「回归」一节。

## 未覆盖 / 未知

1. **`internal/infra/persistence/pg` 覆盖率 80.4%**（门槛 70%，余量 10.4 个百分点）。
   未覆盖的集中在三类：
   - `trade_store.go` 里错误分支的包装路径（`fmt.Errorf("pg: …")`）；
   - `migrate.go`（P0 的迁移执行器，本来就只靠端到端验证，P0 验收已列为已知缺口）；
   - **`isUniqueViolation` / `retryableUniqueError`**：它们只在 `insertConfirmation`
     真的撞唯一约束时才被调用，而咨询锁把同一 `operation_id` 的并发插入串行化了，
     黑盒集成测试无法构造这个冲突。**这条路径的「退化成重放」语义目前只有代码可读，
     没有测试背书**——要测它需要一个测试专用的注入点。
   前两类是「出错时才好走」的代码，价值在排查而不在逻辑，因此没有为了数字去补空测试。
2. **`-race` 未在宿主上执行过。** 本机无 C 编译器且 `CGO_ENABLED=0`，
   `go test -race` 直接报错。纯逻辑包的竞态检测是通过 `golang:1.27` 容器
   挂载模块缓存离线跑过的（`canonical`、`lease` 等包已确认全绿），
   但**这不是宿主 toolchain 的结果**。CI 的 Linux job 有 gcc，会跑完整竞态检测。
3. **`-race` 未覆盖集成测试的并发。** 32/100 并发的验收用例本身在无竞态检测下运行。
   并发正确性目前的背书来自数据库约束与「恰好 1 笔 / 恰好 10 单」这类
   **结果断言**，而不是竞态检测器。
4. **并发争抢下的延迟未纳入验收**（P95 76.5–80.7 ms）。原因是口径问题（已在上文说明），
   但**这不等于并发性能达标**：真实生产负载下的尾部延迟还没有可信数字。
5. **租约的丢失路径只在假后端上验证。** `internal/infra/lease` 的测试用的是内存后端；
   真实 Redis 上的 Lua 原子性、网络分区、主从切换下的语义**没有实测**。
   Redis 侧只有一个「连接不上时返回包装错误、不 panic」的用例。
6. **`SERVER_RESTART` 未在 P1 实现——计划文本与源实现在这一点上不一致。**
   计划 P1 第 7 条写「会话租约：30s 租期 + 5s 心跳续约；租约丢失 → 取消生产者并写
   `SERVER_RESTART`」。逐字核对源实现后确认：30s/5s 这对常量与 `SERVER_RESTART`
   属于 **AG-UI 运行日志租约**（`ag_ui_runtime.py`，P4 范围）；而 Redis 会话租约的
   实际参数是 **30s 租期 + 10s 心跳**（`lease_ms=30000`、`max(10, lease_ms//3)`），
   丢失时 `invalidate()` + `cancel()` 并**不写任何事件**。
   P1 因此实现了租约本体与「丢失 → 作废本地执行权 → 取消生产者」这条语义，
   事件的落库留给 P4。租期与心跳做成了构造参数（默认 30s / 5s），
   改默认值不需要动代码。
7. **`initialize_inventory` 的历史订单占用迁移路径没有真实历史数据可验。**
   测试里用直接写 SQL 的方式造出「订单存在但库存行不存在」的状态；
   真实迁移（从旧库导入）**没有演练过**。
8. **`internal/infra/persistence/pg/pgtest` 覆盖率 30.1%，已豁免。**
   纯函数（库名规范化、哈希、DSN 改写）已 100% 覆盖；
   容器交互部分（起容器、建库、等待就绪）在单元测试里无法验证。
9. **本文件中的性能数字来自本机单次环境**（Docker Desktop for Windows，
   端口映射经过用户态转发），**不代表生产表现**。同一台机器上两次运行的
   P95 相差 26%，说明这个环境的抖动本身就不小。
